# Расширение схемы: что доделывать

Диффер **не** выводит структуру автоматически из схемы — он смотрит на
отдельный декларативный реестр, `src/diff/schemaConfig.ts`. Это сделано
специально: схема ProseMirror описывает, что документ может содержать;
`schemaConfig.ts` описывает, как именно диффер должен обходить и пересобирать
эти узлы. Добавили узел/марку в схему — почти всегда нужно тронуть и
`schemaConfig.ts` (или соседний файл из списка ниже).

## Два слоя схемы

- **`src/schema/src/`** — реальный пакет `@schema` (спеки узлов/марок,
  markdown-парсер, markdown-сериализатор). Портируемый, намеренно **без**
  toDOM/parseDOM для части нод — в реальном приложении рендер живёт отдельно
  (например, React NodeViews). Не трогать эти файлы ради нужд диффера —
  расширять снаружи через `.spec.nodes.update(...)`/`.spec.marks.update(...)`
  (тот же паттерн, которым сам пакет расширяет `prosemirror-markdown`, см.
  `src/schema/src/schema.ts`). Если всё же пришлось поменять что-то внутри
  (как в этом проекте — механические `import type`/enum→const правки под
  `verbatimModuleSyntax`/`erasableSyntaxOnly`, и `"type": "module"` в
  `package.json`, см. предупреждение ниже) — только аддитивно/behavior-preserving.
- **`src/schema/dom.ts`** — "доп. схема для фронта", которую нужен был этот
  проект: берёт спеки из `src/schema/src`, добавляет toDOM/parseDOM для 4 нод,
  у которых их нет вообще (`code_block`, `empty_paragraph`,
  `custom_image_node`, `file_attachment`), добавляет `diffStatus`-attr +
  `data-diff` в toDOM всем диффуемым типам, добавляет 3 presentational
  diff-марки (`diffInsert`/`diffDelete`/`diffFormat`) и виджет `code_block`'а
  под них (`marks: ''` → `marks: 'diffInsert diffDelete diffFormat'`, чисто
  аддитивно). Строит и экспортирует финальную `Schema`, которую использует всё
  приложение.
- **`src/schema/markdown.ts`** — `parseMarkdown()`/`serializeMarkdown()`.
  Реальные `parser`/`serializer` из `src/schema/src` работают со **своим**
  экземпляром `Schema` — другим объектом, хоть имена нод/марок совпадают
  1:1 с `dom.ts`'s, а ProseMirror требует точного совпадения объекта схемы
  для `EditorState`. `parseMarkdown()` поэтому делает JSON re-hydration:
  `schema.nodeFromJSON(baseParser.parse(text).toJSON())` — дёшево по
  сравнению с самим парсингом, недостающие в base-JSON атрибуты (`diffStatus`)
  заполняются дефолтами расширенной схемы автоматически.
- **`src/schema/index.ts`** — точка входа: `schema`, `parseMarkdown`,
  `serializeMarkdown`.

**Ловушка, в которую легко попасть при таком расширении**: если у вложенного
пакета (`src/schema/src/package.json`) нет `"type": "module"`, Node/tsx может
резолвить файлы под ним как CommonJS, тогда как остальной проект — ESM. Оба
модуля тянут `prosemirror-model`, но получают **два разных экземпляра** пакета
(dual package hazard) — `new Schema(...)`, построенный из specs одного
экземпляра, падает с `RangeError: Schema is missing its top node type ('doc')`
при импорте через файл-точку-входа (`tsx scripts/x.ts`), но **не** падает при
`tsx -e "..."` (эта ловушка стоила часа отладки). Если увидите эту ошибку —
первое, что проверить, это `"type"` в ближайшем `package.json` вверх по дереву
от места импорта.

Если что-то забыли — не молчаливый баг: `flatten.ts` вызывает
`warnUnknownNodeType()` при первом же незарегистрированном типе узла и пишет
в консоль `[prose-mirror-diff] Schema node "..." is not registered in
src/diff/schemaConfig.ts`. Это не останавливает рендер (Old/New-просмотр
работает и без регистрации), но в Diff-панели контент такого узла просто
исчезнет.

## Быстрый чек-лист

|---|---|---|---|---|---|---|
| Лист с инлайн-контентом (как paragraph/heading) | нода | если ещё нет toDOM — добавить + `diffStatus` attr + `data-diff` | добавить в `LEAF_NODES`, `attrs()` под все значимые атрибуты (не только "для галочки" — см. предупреждение в п.7) | — | токен, если нужен вход из MD | типографика (подсветка придёт бесплатно) |
| "Пустой" лист (как horizontal_rule/empty_paragraph) | нода | если ещё нет toDOM — добавить + `diffStatus` + `data-diff` | `LEAF_NODES` с `void: true` | — | токен, если нужен вход из MD | типографика |
| Контейнер-обёртка (как blockquote) | нода, `content: "block+"` | — (контейнеры не тонируются напрямую) | `CONTAINER_NODES`, `kind: "wrap"` | — | токен, если нужен вход из MD | — |
| Список-контейнер (как bullet_list) | нода + item-нода | — | `CONTAINER_NODES`, `kind: "list"` | — | токен, если нужен вход из MD | — |
| Марка (как strong) | mark-спека | если нужен свой toDOM | — | `markLabel()`, если атрибуты важны для тултипа | токен, если нужен вход из MD | — |
| Атомарный инлайн-узел (image/mention/emoji) | нода, `inline: true` + `atom: true` | toDOM/parseDOM, если нет | — | обычно не нужна, см. п.6 | токен, если нужен вход из MD | своя подсветка insert/delete/format под тег узла |
| Block-level атом (custom_image_node/file_attachment) | нода, `group:'block'` + `atom:true` | toDOM/parseDOM | `LEAF_NODES` с `void: true` + **обязательно** `attrs()` (см. п.7 — пустой `attrs()` тихо роняет все данные узла при пересборке) | — | токен, если нужен вход из MD | `[data-diff]` на сам тег, не `.diff-insert <tag>` |
| 2D/вложенная структура (как table) | нода(ы) под форму пакета, который вы используете | обычно уже есть (`prosemirror-tables`) | `LEAF_NODES` с `structuredText`, см. п.9 | — | обычно уже есть | типографика + `[data-diff]` на сам узел (и на `<tr>` для строк), не на `margin-left` |

## 1. Новый лист с инлайн-контентом

Пример: `callout` — блок с текстом, как paragraph, но своя семантика.

1. **Нода-спека** — в `src/schema/src` (если это часть портируемой схемы) или
   прямо в `src/schema/dom.ts`, если она специфична для этого вьюера.
   **`src/schema/dom.ts`** — обязательно `diffStatus` в `attrs` (через
   `withDiffStatus()`) и `"data-diff": node.attrs.diffStatus || undefined` в
   `toDOM` (без этого блочная подсветка insert/delete/modified не сработает —
   но это не молчаливая проблема, `warnUnknownNodeType` тут не поможет, потому
   что узел всё равно будет зарегистрирован ниже; просто не будет подсветки
   всей строки).
2. **`src/diff/schemaConfig.ts`** — добавить в `LEAF_NODES`:
   ```ts
   { nodeType: "callout", attrs: (node) => ({ variant: node.attrs.variant }) },
   ```
   `attrs()` можно опустить, если у ноды нет атрибутов, которые должны влиять
   на сравнение ("это та же строка или другая") и переживать rebuild.
3. **`src/styles.css`** — подсветка `data-diff` придёт автоматически
   (селектор `[data-diff]` универсальный), но добавьте типографику под сам
   тег.
4. Опционально — **`src/schema/src/parser`** (`initMarkdownItWithRules()` +
   один из `*ParseSpec` объектов, собираемых в `parser.ts`), если узел должен
   быть достижим из Markdown (см. раздел 8).

## 2. Новый "пустой" лист (без инлайн-контента)

Пример: `page_break`, как `horizontal_rule`/`empty_paragraph`.

Всё как в п.1, но в `schemaConfig.ts` — `{ nodeType: "page_break", void: true }`.
`void: true` само по себе покрывает и рендер, и rebuild (`flatten.ts`'s
`buildLeaf`/`isVoidLeaf`, `diffDoc.ts`'s `toRenderLine` уже обобщены и не
завязаны на конкретное имя узла) — **но** если у ноды есть значимые атрибуты
(не только `diffStatus`), нужен ещё и `attrs()`, см. п.7 — `void: true` без
него значит "эта нода никогда не диффится по-другому, кроме позиции", что для
пустого разделителя типа `horizontal_rule` верно, а для атома с данными типа
`custom_image_node` — нет.

## 3. Новый контейнер-обёртка (`block+` напрямую, как blockquote)

Пример: `aside`.

1. **Спека** (`src/schema/src` или `src/schema/dom.ts`) — `content: "block+"`.
2. **`src/diff/schemaConfig.ts`** — добавить в `CONTAINER_NODES`:
   ```ts
   { kind: "wrap", nodeType: "aside" },
   ```
Больше ничего: `walk()`/`rebuildLevel()` в `flatten.ts` обходят и
пересобирают любой `"wrap"`-контейнер одинаково (и для пустого случая сами
спрашивают у схемы её `createAndFill()`-дефолт, а не хардкодят `paragraph`).

## 4. Новый список-контейнер (айтемы, как bullet_list/list_item)

Пример: `task_list` + `task_item` (чек-лист).

1. **Спека** — `task_list: { content: "task_item+" }`,
   `task_item: { content: "paragraph+" }` (см. ограничение ниже).
2. **`src/diff/schemaConfig.ts`**:
   ```ts
   { kind: "list", nodeType: "task_list", itemType: "task_item" },
   ```

**Известное ограничение**, которое этот рефакторинг не снимает: элемент
списка обрабатывается как ровно один leaf-блок (см. `list_item`/`task_item`
в текущей схеме — `content: "paragraph+"`, но диффер разворачивает только
первый уровень). Несколько параграфов или вложенный список внутри одного
элемента списка не развернутся в отдельные диффуемые строки — лишний
контент будет либо отброшен при пересборке (`type.createAndFill` молча
подгонит под `content` выражение), либо не подсветится корректно. Если это
нужно — придётся научить `walk()`/`rebuildLevel()` работать с
многоуровневым path per-item (сейчас item сам по себе "прозрачен" и не
добавляет сегмент в `path`), это уже не входит в объём деклативного конфига.

## 5. Новая марка

Пример: `highlight` (маркер-выделение).

1. **Mark-спека** (`src/schema/src` или `src/schema/dom.ts`, если марка
   специфична для этого вьюера, как diff-марки сами). Марка не требует записи
   в `schemaConfig.ts` — марки видит `inlineDiff.ts` через
   `node.marks`/`child.marks`, а не через реестр узлов.
2. **`src/diff/inlineDiff.ts`**, функция `markLabel()` — если у марки есть
   значимые атрибуты (как `href` у `link`), добавьте туда ветку, иначе в
   подсказке `diffFormat` (при наведении на изменение форматирования) она
   покажется просто именем типа марки без деталей:
   ```ts
   function markLabel(mark: Mark): string {
     if (mark.type.name === "link") return `link(${mark.attrs.href})`;
     if (mark.type.name === "highlight") return `highlight(${mark.attrs.color})`;
     return mark.type.name;
   }
   ```
3. Если у какого-то узла ограничен набор марок (`marks: "..."`, как у
   `code_block` — в базовом пакете `marks: ''`, `src/schema/dom.ts` расширяет
   до `'diffInsert diffDelete diffFormat'`) и туда нужно пускать новую марку —
   добавьте её в список **в `dom.ts`**, а не в `src/schema/src`. Три служебные
   diff-марки должны оставаться в allow-list у любого узла с ограничением —
   без них диффер падает с `RangeError: Invalid content for node ...` при
   попытке подсветить изменение внутри такого узла (реальный баг, который уже
   ловился на `code_block` дважды — один раз в этом проекте, один раз при
   переносе на реальную схему).
4. Опционально — токен в `src/schema/src/parser` (раздел 8).

## 6. Новый атомарный инлайн-узел (не текст)

Пример уже в схеме и работает "бесплатно", без единой строчки в этом
проекте: `hard_break` (`<br>` внутри параграфа — наследует toDOM из
`prosemirror-markdown`, ничего своего добавлять не пришлось). Раньше здесь
был пример с картинкой, но в реальной схеме `custom_image_node`
**блочный**, не инлайновый (см. п. "Block-level атом" в чек-листе и
раздел 7) — так что за примером инлайн-атома теперь сюда, а не к картинкам.

Раньше это было самое хрупкое место (любой нетекстовый инлайн-узел молча
выпадал из diff-пайплайна), теперь это общий механизм в
`src/diff/inlineDiff.ts`:

- `flattenInlineNode()` кладёт в `CharUnit[]` не только текстовые символы, но
  и один "неделимый юнит" на каждый нетекстовый inline-child: `ch:
  ATOMIC_PLACEHOLDER` (U+FFFC, object replacement character — суррогат для
  посимвольного Myers-выравнивания) + `node: PMNode` — ссылка на сам узел.
- Выравнивание (`charUnitsEqual`) сравнивает такие юниты не по `ch` (он у всех
  одинаковый), а по **содержимому узла** — `node.type` + `JSON.stringify(node.attrs)`
  (`atomicContentEqual()`). Марки (например, `link`, если картинка обёрнута в
  ссылку) сравниваются отдельно, как и для текста — та же связка "выравнивание
  по контенту, декорации отдельным слоем", что и у символов.
- **Практическое следствие**: два атомарных узла с одинаковым типом, но
  разными атрибутами, никогда не считаются "equal" на этом уровне — значит
  расхождение всегда попадёт в diff как delete+insert этого узла, а не тихо
  пройдёт как "ничего не изменилось". Тот же принцип, что и в п.7 для
  block-level атомов (`custom_image_node`/`file_attachment`) — там это
  реализовано иначе (через `attrs()` + void-leaf сравнение в `diffDoc.ts`),
  но мотивация та же: "если содержимое узла другое — должен быть дифф".
- Каждый такой юнит — всегда свой отдельный `Run` (никогда не сливается с
  соседями, даже если у них случайно совпал `groupKey`) — см. `groupKey:
  atomic:${counter}` в `diffInline()`.
- `buildLeaf()` (`flatten.ts`) и `wholeLineRuns()` (`diffDoc.ts`) при сборке
  рана проверяют `run.node`: если он есть — пересоздают исходный узел
  (`node.type.create(node.attrs, null, run.marks)`) вместо `schema.text(...)`.

Что нужно сделать при добавлении **нового** атомарного инлайн-узла:

1. **Спека** — `inline: true`, обычно `atom: true`, свои `attrs`.
2. **`src/schema/dom.ts`** — toDOM/parseDOM, если у спеки их ещё нет.
3. **`src/schema/src/parser`** — токен, если нужен вход из Markdown.
4. **`src/styles.css`** — своя подсветка insert/delete/format для тега узла;
   универсального `.diff-insert <tag>`-стиля нет, он специфичен под конкретный
   тег (было под `<img>`, пока картинка была инлайновой).

`warnUnknownNodeType()` по-прежнему не покрывает инлайн-узлы (он ловит только
неизвестные типы на уровне блоков) — так что после добавления нового
атомарного узла стоит вручную прогнать сценарий insert/delete/format через
`scripts/smoke.ts`.

## 7. Просто новый/изменённый атрибут на существующей ноде

- Если атрибут должен влиять на "это та же строка или другая" (участвует в
  `lineSignature`) и должен переживать диффинг — добавьте его в `attrs()`
  соответствующего конфига в `LEAF_NODES` (`schemaConfig.ts`).
- Если нет (чисто косметический, не диффится) — можно не трогать: PM просто
  проигнорирует лишний ключ при `type.create(attrs, ...)`, но после диффа он
  вернётся к дефолтному значению схемы (не сохранится).

**Два реальных бага, пойманных при переносе на настоящую схему** — оба варианта
неполного `attrs()`:

1. **Забыли `attrs()` вообще** — `custom_image_node`/`file_attachment`
   зарегистрировали как `{ void: true }` без `attrs()`. Результат: **все**
   атрибуты узла (`downloadUrl`, `fileName`, ...) молча обнулялись до
   дефолтов схемы при пересборке — картинка в diff-панели превращалась в
   сломанную ссылку независимо от того, что было в исходном документе. Не
   "не сравнивается" — **не сохраняется**, вот в чём разница с "косметическим"
   случаем выше: у void-листа `attrs()` — это единственный канал, через
   который его данные вообще попадают в rebuild.
2. **`attrs()` захватил *слишком много*** — исправление (1) как `{
   ...node.attrs }` завело в другую ловушку: `custom_image_node.localId` —
   это `crypto.randomUUID()`, который парсер генерирует заново при **каждом**
   разборе (`media.parse-spec.ts`), так что даже полностью неизменная
   картинка получала разный `localId` в old/new — и out различался, и старая
   структурная (`structural`) сверка пар никогда не признавала её "той же
   картинкой". `attrs()` пришлось сузить до явного allow-list полей, которые
   реально определяют "это тот же файл" (`attachmentId`, `fileName`,
   `downloadUrl`, `mimeType`, `fileType`, ширина/высота) — не эфемерного
   рантайм-состояния (`localId`, `status`, `progress`).

Вывод: `attrs()` — это одновременно "что сравнивается" и "что переживает
rebuild" для **этого конкретного узла**, не для схемы вообще. Для void-листа
с непустыми attrs — не пропускайте этот шаг; и включайте только то, что
семантически идентифицирует контент, а не служебные/рантайм поля.

## 8. Доступность из Markdown

`src/schema/src/parser` — это **отдельная** декларативная точка входа
(`MarkdownParser` из `prosemirror-markdown`, собранная в `parser.ts` из
нескольких `*ParseSpec`-объектов — `default.parse.spec.ts`,
`code.parse.spec.ts`, `table-block.parse.spec.ts`, `media.parse-spec.ts`,
`link-block.parse.spec.ts`), она не связана с `schemaConfig.ts` напрямую (и
эти файлы — часть портируемого `@schema`-пакета, трогать по общему правилу
раздела "Два слоя схемы" вверху). Если новый узел/марка должны быть достижимы
из Markdown-режима UI — добавьте токен в подходящий `*ParseSpec` объект (или
заведите новый и добавьте в спред внутри `parser.ts`):

```ts
strike: { mark: "strike" }, // markdown-it уже включает 'strikethrough'
                             // в initMarkdownItWithRules()
```

Если у markdown-it появится токен, для которого нет записи ни в одном из этих
объектов, `MarkdownParser.parse()` бросит `Error: Token type "..." not
supported by Markdown parser` — это ловится в UI (`App.tsx`,
`tryParseMarkdown`) и показывается под textarea, но лучше не доводить до
этого: при включении любого нового markdown-it-плагина/правила сразу
проверяйте, какие новые типы токенов оно добавляет
(`initMarkdownItWithRules()` в `parser/init-markdown-it.ts`). Для GFM-таблиц
конкретно есть ловушка, уже решённая в пакете — `blockTableCellRule`
(`parser/rule-override.ts`) оборачивает голый текст ячейки в параграф до того,
как токены доходят до `MarkdownParser`: без этого `td.content` не проходит
content-модель `table_cell` (`block+`), и `MarkdownParser`'s `createAndFill`
**молча** роняет содержимое ячейки, без ошибки — тот же класс бага, что и
неполный `attrs()` в разделе 7 (данные пропадают тихо, не с исключением).

## 9. Таблицы (`table`/`table_row`/`table_cell`/`table_header`)

Ноды — это реальный `prosemirror-tables` (`tableNodes()`, вызван в
`src/schema/src/blocks/table-block/table-block.spec.ts`): `table` — это
`table_row+`, строка — `(table_cell | table_header)*`, ячейка — `block+` с
`colspan`/`rowspan`/`colwidth`/`background`. Пакет даёт `table`/`table_row`/
`table_cell`/`table_header` уже с toDOM/parseDOM — `dom.ts` добавляет
`diffStatus`+`data-diff` только `table`/`table_row` (у ячеек их не нужно,
подсветка целиком идёт через их содержимое). Интерактивный плагин
`prosemirror-tables` (resize колонок, выделение ячеек) в схему не подключён —
этот вьюер read-only, он не нужен.

Это не укладывается в `wrap`/`list` — обе модели одномерные, а таблица
(строка × ячейка, плюс `block+` внутри ячейки) требует минимум двух
дополнительных уровней вложенности с индексами. Вместо новой рекурсивной
модели `table` зарегистрирован как **leaf** с одним специальным хуком в
`LeafNodeConfig` (`schemaConfig.ts`), применимым и к будущим похожим случаям:

- **`structuredText`** — вместо `flattenInlineNode()` (который ждёт плоский
  инлайн-контент) даёт `plainText` через `node.textContent` (рекурсивно
  собирает весь текст из всех ячеек, ничего не зная о структуре таблицы) и
  сигнализирует, что `flatten.ts` должен сохранить сам узел в `Line.node` —
  без этого у `diffDoc.ts` не было бы доступа к строкам/ячейкам для
  рекурсивного диффа.

**Что реально диффится** (`diffDoc.ts`, `toRenderTableLine()` +
`pairTableRows()`/`renderTableRow()`): таблица участвует в диффе документа как
обычный leaf (может целиком стать delete+insert, если ей вообще не нашлось
пары на другой стороне), но если пара нашлась — её **строки** гоняются через
свой собственный LCS (`diffArrays` + пере-паринг соседних delete/insert-рядов
в "modify", той же формы, что и `pairAdjacentReplacements()` для строк
документа, только над `PMNode`-строками, а не `Line`):

- совпавшая (`equal`/`modify`) пара строк — всегда **одинаковой формы ячеек**
  (тип/colspan/rowspan), это гарантия конструкции (см. ниже) — зиплюется по
  индексу и каждая пара ячеек уходит в `diffBlocks()` рекурсивно — обычный
  cell-content diff.
- несовпавшая строка — просто delete или insert **этой одной строки**
  (`data-diff` на `<tr>`, см. `styles.css`) — это и есть тот случай "строка
  добавлена/удалена", который раньше (до этого раздела) схлопывал всю
  таблицу в opaque replace.

**Паринг строк (`rowsMatchForPairing()`) сознательно НЕ следует
structural/similarity тумблеру документа** — в отличие от
`linesMatchForPairing()`, он всегда требует и совпадения формы ячеек, и
похожести текста (`textSimilarity()` на `row.textContent`) одновременно.
Это не всё равно: structural-паринг "игнорируем контент, сопоставляем по
форме" имеет смысл для блочного контента, где сам тип узла (paragraph vs
heading vs ...) — уже значимый сигнал. Для строк таблицы это вырождается в
"сопоставляем по позиции" — почти в любой реальной таблице все строки имеют
одинаковую форму ячеек. Без этой поправки (была реальным багом одну сессию)
удалённая строка и никак не связанная с ней вставленная строка той же формы
насильно сопоставлялись в "modify" и показывались как посимвольная замена
("Alpha" → "Gamma") вместо чистых delete+insert.

Сам рекурсивный дифф ячеек не изменился: `diffDocuments()` разложен на
переиспользуемый `diffBlocks()` (flatten → diffArrays →
pairAdjacentReplacements → toRenderLine), который вызывается **рекурсивно** на
паре `flattenDoc(oldCell)` / `flattenDoc(newCell)`. Результат каждой ячейки
собирается обратно через `rebuildBlocks()` (экспортированная версия
`rebuildLevel()` из `flatten.ts`) и вставляется как `content` пересозданной
`table_cell`/`table_header` ноды — `RenderLine.prebuiltNode` (эскейп-люк в
`buildLeaf()`) отдаёт получившийся `table`-узел как есть, в обход обычной
сборки attrs+runs, которая рассчитана на плоский инлайн-контент.

`stats` передаётся в рекурсивные вызовы по ссылке — счётчики (`insertedChars`,
`modifiedLines` и т.д.) из строк и ячеек автоматически суммируются в общую
статистику документа, ничего специально агрегировать не нужно.

**Осознанно не сделано**: диффа **колонок** нет — если в реальности добавили
колонку (а не строку), это увидится как "у каждой строки форма ячеек не
совпала" → каждая строка откатится на delete+insert по отдельности, а не
покажется как "одна новая колонка". Полный 2D-дифф (LCS по строкам И по
колонкам одновременно) — отдельная, более крупная задача.

## Итог

`src/schema/src/` → *что документ может содержать* — портируемые спеки/
парсер/сериализатор, без toDOM/parseDOM, не трогать ради нужд диффера.
`src/schema/dom.ts` → *как это рендерится* — toDOM/parseDOM для нод, у
которых их не было, `diffStatus`/`data-diff` на диффуемых типах, diff-марки.
Единственный модуль, который строит финальную `Schema`.
`schemaConfig.ts` → *как диффер обходит и пересобирает структуру* (одна
точка для узлов уровня блоков/контейнеров) — и `attrs()` здесь же решает,
что из атрибутов узла вообще видно дифферу (см. предупреждение в разделе 7).
`inlineDiff.ts` → *как сравниваются символы и марки внутри строки* (марки
регистрировать не нужно, инлайн-узлы — нужно, и это ручная работа).
`src/schema/src/parser` → *что достижимо из Markdown-входа* (отдельный
реестр внутри портируемого пакета, трогать только если нужен вход из MD).
`styles.css` → блочная подсветка `[data-diff]` универсальна, руками нужна
только типографика под новый тег.
