# Расширение схемы: что доделывать

Диффер **не** выводит структуру автоматически из `src/schema.ts` — он смотрит
на отдельный декларативный реестр, `src/diff/schemaConfig.ts`. Это сделано
специально: схема ProseMirror описывает, что документ может содержать;
`schemaConfig.ts` описывает, как именно диффер должен обходить и пересобирать
эти узлы. Добавили узел/марку в схему — почти всегда нужно тронуть и
`schemaConfig.ts` (или соседний файл из списка ниже).

Если что-то забыли — не молчаливый баг: `flatten.ts` вызывает
`warnUnknownNodeType()` при первом же незарегистрированном типе узла и пишет
в консоль `[prose-mirror-diff] Schema node "..." is not registered in
src/diff/schemaConfig.ts`. Это не останавливает рендер (Old/New-просмотр
работает и без регистрации), но в Diff-панели контент такого узла просто
исчезнет.

## Быстрый чек-лист

| Что добавляете | `schema.ts` | `schemaConfig.ts` | `inlineDiff.ts` | `fromMarkdown.ts` | `styles.css` |
|---|---|---|---|---|---|
| Лист с инлайн-контентом (как paragraph/heading) | нода + `diffStatusAttr` + `data-diff` в toDOM | добавить в `LEAF_NODES` | — | если нужен вход из MD | типографика (подсветка придёт бесплатно) |
| "Пустой" лист (как horizontal_rule) | нода + `diffStatusAttr` + `data-diff` | `LEAF_NODES` с `void: true` | — | если нужен вход из MD | типографика |
| Контейнер-обёртка (как blockquote) | нода, `content: "block+"` | `CONTAINER_NODES`, `kind: "wrap"` | — | если нужен вход из MD | — |
| Список-контейнер (как bullet_list) | нода + item-нода | `CONTAINER_NODES`, `kind: "list"` | — | если нужен вход из MD | — |
| Марка (как strong) | mark-спека | — | `markLabel()`, если атрибуты важны для тултипа | если нужен вход из MD | — |
| Атомарный инлайн-узел (image/mention/emoji) | нода | — | **нужна доработка**, см. ниже | если нужен вход из MD | — |
| Атрибут на существующей ноде | добавить в attrs | добавить в `attrs()` соответствующего leaf-конфига, если должен влиять на сравнение строк | — | обновить `getAttrs` токена, если пришло из MD | — |

## 1. Новый лист с инлайн-контентом

Пример: `callout` — блок с текстом, как paragraph, но своя семантика.

1. **`src/schema.ts`** — node-спека, обязательно с `...diffStatusAttr` в
   `attrs` и `"data-diff": node.attrs.diffStatus || undefined` в `toDOM`
   (без этого блочная подсветка insert/delete/modified не сработает — но это
   не молчаливая проблема, `warnUnknownNodeType` тут не поможет, потому что
   узел всё равно будет зарегистрирован ниже; просто не будет подсветки
   всей строки).
2. **`src/diff/schemaConfig.ts`** — добавить в `LEAF_NODES`:
   ```ts
   { nodeType: "callout", attrs: (node) => ({ variant: node.attrs.variant }) },
   ```
   `attrs()` можно опустить, если у ноды нет атрибутов, которые должны влиять
   на сравнение ("это та же строка или другая") и переживать rebuild.
3. **`src/styles.css`** — подсветка `data-diff` придёт автоматически
   (селектор `[data-diff]` универсальный), но добавьте типографику под сам
   тег.
4. Опционально — **`src/markdown/fromMarkdown.ts`**, если узел должен быть
   достижим из Markdown (см. раздел 6).

## 2. Новый "пустой" лист (без инлайн-контента)

Пример: `page_break`, как `horizontal_rule`.

Всё как в п.1, но в `schemaConfig.ts` — `{ nodeType: "page_break", void: true }`.
`void: true` — это единственное, что нужно: `flatten.ts` (`buildLeaf`,
`isVoidLeaf`) и `diffDoc.ts` (`toRenderLine`) уже обобщены и не завязаны на
конкретное имя `horizontal_rule` — они спрашивают `isVoidLeaf(nodeType)`.

## 3. Новый контейнер-обёртка (`block+` напрямую, как blockquote)

Пример: `aside`.

1. **`src/schema.ts`** — `content: "block+"`.
2. **`src/diff/schemaConfig.ts`** — добавить в `CONTAINER_NODES`:
   ```ts
   { kind: "wrap", nodeType: "aside" },
   ```
Больше ничего: `walk()`/`rebuildLevel()` в `flatten.ts` обходят и
пересобирают любой `"wrap"`-контейнер одинаково.

## 4. Новый список-контейнер (айтемы, как bullet_list/list_item)

Пример: `task_list` + `task_item` (чек-лист).

1. **`src/schema.ts`** — `task_list: { content: "task_item+" }`,
   `task_item: { content: "paragraph+" }` (см. ограничение ниже).
2. **`src/diff/schemaConfig.ts`**:
   ```ts
   { kind: "list", nodeType: "task_list", itemType: "task_item" },
   ```

**Известное ограничение**, которое этот рефакторинг не снимает: элемент
списка обрабатывается как ровно один leaf-блок (см. `list_item`/`task_item`
в текущей схеме — `content: "paragraph+"`, но диффер разворачивает только
первый уровень). Несколько параграфов или вложенный список внутри одного
элемента списка не развернутся в отдельные диффуемые строки — лишний
контент будет либо отброшен при пересборке (`type.createAndFill` молча
подгонит под `content` выражение), либо не подсветится корректно. Если это
нужно — придётся научить `walk()`/`rebuildLevel()` работать с
многоуровневым path per-item (сейчас item сам по себе "прозрачен" и не
добавляет сегмент в `path`), это уже не входит в объём деклативного конфига.

## 5. Новая марка

Пример: `highlight` (маркер-выделение).

1. **`src/schema.ts`** — mark-спека. Марка не требует записи в
   `schemaConfig.ts` — марки видит `inlineDiff.ts` через
   `node.marks`/`child.marks`, а не через реестр узлов.
2. **`src/diff/inlineDiff.ts`**, функция `markLabel()` — если у марки есть
   значимые атрибуты (как `href` у `link`), добавьте туда ветку, иначе в
   подсказке `diffFormat` (при наведении на изменение форматирования) она
   покажется просто именем типа марки без деталей:
   ```ts
   function markLabel(mark: Mark): string {
     if (mark.type.name === "link") return `link(${mark.attrs.href})`;
     if (mark.type.name === "highlight") return `highlight(${mark.attrs.color})`;
     return mark.type.name;
   }
   ```
3. Если у какого-то узла ограничен набор марок (`marks: "..."`, как у
   `code_block` в `schema.ts`) и туда нужно пускать новую марку —
   добавьте её в список. Три служебные diff-марки (`diffInsert diffDelete
   diffFormat`) должны оставаться в allow-list у любого узла с ограничением
   — без них диффер падает с `RangeError: Invalid content for node ...` при
   попытке подсветить изменение внутри такого узла (реальный баг, который
   уже ловился на `code_block`).
4. Опционально — токен в `fromMarkdown.ts` (раздел 6).

## 6. Новый атомарный инлайн-узел (не текст) — САМОЕ ХРУПКОЕ МЕСТО

Пример: `image`, `mention`, `emoji`, `hard_break`.

Это единственный класс изменений, который декларативный конфиг **не**
покрывает и который сейчас не поддержан вообще:
`flattenInlineNode()` в `src/diff/inlineDiff.ts` итерируется только по
`child.isText` — любой нетекстовый инлайн-узел молча выпадает при проходе
через diff-пайплайн. Не крашится, не варнинг — просто исчезает из
Diff-панели (в "сыром" Old/New-просмотре он будет на месте, т.к. тот не идёт
через `flattenInlineNode`).

Если такой узел нужен в диффе, придётся:

1. В `flattenInlineNode()` — при встрече нетекстового инлайн-узла добавлять
   в `CharUnit[]` не символ, а "неделимый юнит", представляющий весь узел
   целиком (например, с `ch: "￼"` — object replacement character — как
   суррогат для посимвольного LCS, плюс ссылку на сам PM-узел).
2. В `diffInline()`/`finishChunk()` (`inlineDiff.ts`) и `buildLeaf()`
   (`flatten.ts`) — при сборке текстового рана проверять, не является ли
   юнит таким суррогатом, и в этом случае вставлять оригинальный узел
   (обёрнутый в diff-марку, если он insert/delete), а не `schema.text(...)`.

Если такой узел встретится без этой доработки — `warnUnknownNodeType()` тут
не сработает (он ловит только неизвестные **типы узлов на уровне блоков**,
а не пропущенные инлайн-узлы), так что это единственное место, где стоит
вручную протестировать сценарий insert/delete через `scripts/smoke.ts` после
добавления такого узла.

## 7. Просто новый/изменённый атрибут на существующей ноде

- Если атрибут должен влиять на "это та же строка или другая" (участвует в
  `lineSignature`) и должен переживать диффинг — добавьте его в `attrs()`
  соответствующего конфига в `LEAF_NODES` (`schemaConfig.ts`).
- Если нет (чисто косметический, не диффится) — можно не трогать: PM просто
  проигнорирует лишний ключ при `type.create(attrs, ...)`, но после диффа он
  вернётся к дефолтному значению схемы (не сохранится).

## 8. Доступность из Markdown

`src/markdown/fromMarkdown.ts` — это **отдельная** декларативная точка входа
(`MarkdownParser` из `prosemirror-markdown`, сконфигурированный под нашу
схему), она не связана с `schemaConfig.ts` напрямую. Если новый узел/марка
должны быть достижимы из Markdown-режима UI — добавьте токен в объект,
переданный в `new MarkdownParser(schema, md, { ... })`:

```ts
strike: { mark: "strike" }, // потребует markdown-it-плагин: CommonMark
                             // без него не парсит ~~зачёркнутый~~
```

Если у markdown-it появится токен, для которого нет записи в этом объекте,
`MarkdownParser.parse()` бросит `Error: Token type "..." not supported by
Markdown parser` — это ловится в UI (`App.tsx`, `tryParseMarkdown`) и
показывается под textarea, но лучше не доводить до этого: при включении
любого нового markdown-it-плагина/правила сразу проверяйте, какие новые типы
токенов оно добавляет.

## Итог

`schema.ts` → *что документ может содержать*.
`schemaConfig.ts` → *как диффер обходит и пересобирает структуру* (одна
точка для узлов уровня блоков/контейнеров).
`inlineDiff.ts` → *как сравниваются символы и марки внутри строки* (марки
регистрировать не нужно, инлайн-узлы — нужно, и это ручная работа).
`fromMarkdown.ts` → *что достижимо из Markdown-входа* (отдельный реестр,
трогать только если нужен вход из MD).
`styles.css` → блочная подсветка `[data-diff]` универсальна, руками нужна
только типографика под новый тег.
